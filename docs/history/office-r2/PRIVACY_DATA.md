## Office 转换生成的临时副本

本地预览会将输入复制到专属任务目录，创建 LibreOffice 用户 profile 和临时 PDF，再向调用者指定的输出位置写入结果。转换本身不需要模型请求；若后续由模型读取文档／图片，仍按相应模型授权与费用处理。输出 PDF 是新的文档副本，应按使用目的纳入保存与删除范围。

引擎 `TEMP`／`TMP` 也放在本次任务目录。必要的 Windows 8.3 短名称只引用经身份核验的同一目录，不另建正文副本或共享存储。启动设置禁用 LibreOffice 自身的已知崩溃转储开关；这不承诺阻止 Windows 或外部诊断软件产生其自身记录，也不能把没有 PDF 的失败当作成功。

正常结束和可确认的失败收尾会清理本次任务临时目录；进程归属或清理无法确认时保留现场并明确报错，不宣称已经删除。库内设置禁用 Python 字节码写入，避免测试／使用路径落入程序目录。未知的旧临时目录不能直接按通配符全盘清理。独立 profile 与 Windows Job 只管理本次进程生命周期，不构成 OS 文件／网络安全沙箱；不要据此认为恶意文档的所有外部访问均被系统拦截。


文档基线：2026-09-21，Windows x64。当前日常修订为 `sep-alpha2-stability-20260921`，DSH `0.1.6-alpha.2`，程序图以 `ffb961a1…` 开头。历史 `20260920-r2-sanitized` Only / Full ZIP 的程序图为 `e57816d0…`；本次 `20260921-office-r2` 候选基于最新修复另行生成，新包隐私扫描状态单独记录。版本关系见[发布说明](RELEASE_NOTES.md)。本页说明实际数据流程，不作“所有内容永不外发”或操作系统级隔离承诺。

## 保存什么，保存在哪里

以下 `<安装目录>` 是用户选择的新实例目录，不是开发者电脑路径。表中位置对应现有 Only / Full 安装器；日常迁移实例可能使用不同布局，以 `deployment-rc2.json` 的路径字段和实际插件配置为准。请勿仅凭表格移动、覆盖或删除目录。

| 数据 | 默认位置或定位方式 | 作用与敏感性 |
|---|---|---|
| 用户项目与原文件 | `<安装目录>/workspace`，或用户明确选择的项目根；RAG 来源由 `projects[].sources` 指定 | 用户原稿、代码、附件。索引不等于原文件搬移。 |
| 会话和工具历史 | `<安装目录>/home/sessions`；由会话持久化插件的 `root` 指定 | 可能含原话、助手回复、工具输入输出、审阅内容及路径。记忆关闭后仍可能保存正常对话。 |
| RAG、活跃记忆、归档 | `<安装目录>/data/storage`；对应 `storageRoot` | 三个受管 JSON 数据域：`dsh_enhancement_suite_v1`、`dsh_four_layer_memory_v1`、`dsh_four_layer_archive_v1`。包含索引片段、来源、修订和提炼回执等。内部历史名称为兼容保留。 |
| 记忆治理、删除依据、快照和暂存 | `<storageRoot>/.suite-memory/p2` 下的登记目录 | 支持提交、恢复、防止旧内容重新出现及纳管清理；部分备份、暂存包含正文，不是普通无敏感性日志。 |
| 文件恢复副本、插件源版本 | 文件恢复配置 `recovery.root`、插件持久化配置 `persistence.root` | 与记忆库不同，可能保存文件原文和插件代码。须按对应恢复机制处理。 |
| 桌面、守护与运行状态 | `<安装目录>/state`；Electron、控制中心、锁路径由部署配置指定 | 窗口状态、连接身份、故障记录等；部分记录含本机路径和标识。 |
| API Key | 默认 `<安装目录>/.env` 中的 `DEEPSEEK_API_KEY` | 由本机服务读取并用于认证，不应贴到聊天、记忆、问题报告或仓库。该文件不是加密保险库。 |
| 用量与预算 | 套件配置中的 `budgetPath` | 预留、结算、未知结果等记录。不能删账本或重建实例来假定已发生费用归零。 |

新分发安装建立空白业务库，不自动复制已有 DSH 的私人数据、API Key、会话、自装插件或预算。历史 r2 脱敏 ZIP 已对已知开发路径、密钥模式、私人配置及 Git 元数据进行扫描；本次候选须按最终归档重新核验，实际状态见测试摘要。模式扫描不是任意秘密检测的完备证明。使用后产生的本地安装回执和日志可能包含用户自己的路径。

## 四层记忆和项目边界

L1 是模型请求的上下文窗口；L2 是项目资料、事项及临时记忆；L3 是稳定偏好、重要个人事实与项目总目标；L4 保存受管历史与归档。L2 / L3 属于模型外持久存储与检索，不改变模型权重。现行文本检索采用本地 BM25，不依赖完整 Mem0 云服务或另一套 Mem0 向量库。

Mem0 辅助提炼仅从**当前项目允许的直接用户对话**选取内容，排除其他项目、归档、撤回和禁止记忆内容；候选仍须通过 SEP 的来源与生命周期规则再进入已有受管库。它不是跨项目聊天聚合器。

项目配置显式绑定相同 `userProfile` 时，已获准的 L3 偏好与个人事实可共享。项目目标、项目资料和事项继续按项目隔离；共享 L3 不交给 Mem0 当作其他项目对话提炼。该绑定是本机配置规则，不是多用户账号认证或防恶意同进程代码的边界。

L4 不自动加入普通回答；明确历史需求才开放相应受限检索或原文展开。关闭“自动学习”阻止后续自动提炼，关闭“自动引用”阻止后续自动选入；两者均不删除已有记录，也不撤销已经发送的模型请求。原生会话中已经出现的内容另行保存，不能靠关闭开关让供应商或历史对话“忘记”。

## 何时会向外部发送内容

| 触发动作 | 可能离开本机的内容 | 当前控制范围 |
|---|---|---|
| 正常模型请求、自动记忆提炼、摘要压缩 | 构建请求时选入的对话、工具结果、相关记忆或资料片段 | 发送到实际配置的模型服务；模型白名单、预算和请求限额分别生效。关闭自动记忆不等于关闭正常模型调用。 |
| Mem0 辅助抽取 | 当前项目筛选后的用户消息及提炼提示 | 使用 SEP 的模型适配与共享账本；本集成未接入 Mem0 云存储。 |
| 视觉分析 | 被选中的图片及提示；依工具与配置而定 | 项目允许图片上传且实际调用时才发送；当前模板允许已配置项目使用该能力，不应将图片解析描述为一律离线。 |
| `suite_delegate` 工作前评测 | 固定合成题、提示和目标模型配置 | 会产生模型请求与费用；不以私人对话作为评测题。不等于官方 PinchBench 排行榜上传。 |
| 检查 DSH 更新 | 官方发布查询、常规网络连接信息 | 向官方 GitHub 发布接口查询，不调用模型；启动及运行每三小时检查不等于自动安装。 |
| 用户启用的 MCP、搜索或其他插件 | 由相应工具输入和实现决定 | 不在 SEP 内置记忆项目过滤的统一保证范围；应检查插件来源及其数据说明。 |
| 可选公开仓库评测 | 获准的公开实例、补丁与评测产物，按受控后端配置处理 | 评测入口和上下文准备默认关闭；不是任意私人仓库上传入口。 |

本地建立 RAG 索引本身不要求把整个资料库发给模型；检索片段一旦进入模型请求，就属于该次外部发送。第三方供应商的留存、地域和账号条款不由本地删除机制控制。

## 遥测和日志的实际配置

已核对当前日常 `cordis.patch.yml` 及现有脱敏分发模板：`session-log-deepseek` 为 `disabled: true` 且 `config.enabled: false`，`session-telemetry-otel` 为 `disabled: true`。上游相关包仍随宿主保留；这是受管配置禁用，不是删除所有遥测代码或覆盖任意用户后续配置。其他插件启用、环境变动或用户改配置后，应重新核对。

上述禁用不关闭本地会话持久化、预算记账、恢复审计，也不拦截正常模型、图片、更新和外部工具请求。自动记忆 HTTP 诊断仅保留有限状态码与错误分类，不保存供应商响应正文；不能推导为所有插件、所有日志都已自动脱敏。

对外提供日志前，应检查正文、用户名、绝对路径、邮箱、项目名称、会话标识、内网地址、认证头、Cookie、Key 和工具参数；尽量以合成资料复现。详见[问题反馈](SUPPORT.md)。

## 首次纳管与历史范围

首次纳管会按记录展示正文、修订、作用域、状态、时间和省略历史的情况，精确选择确认只授权暂存；正式发布与业务开放另走受控计划。当前流程不把原 L4、旧修订、备份、旧索引和缓存一并恢复为活跃内容，保留原库的安排必须单独说明。

导入保留原 `createdAt`、`updatedAt`、有效使用时间 `lastUsedAt`、任务结束时间 `closedAt` 及适用到期字段；纳管提交时间单独记为 `adoptedAt`。审阅和确认不刷新活跃时间，不给过期临时事项重新计算保留期。缺失或无法解释的时间会被排除，已到归档期或过期的记录不能靠导入直接重新启用。

预览元数据、按需正文审阅、捕获副本、暂存和失败现场不应统称为“不纳管的旧历史”：流程新增正文须按副本账本登记并受下述期限和删除规则约束。终端审阅输出如被用户重定向或外部工具录制，会形成另外的副本，不应自动认定其已被受管清理。

## 归档、清理和删除的区别

- 活跃事项按当前规则评估归档：完成或取消的任务至少 7 天，未确认候选与无有效使用的临时事项通常 30 天，结束项目的目标至少 30 天且无未结任务。置顶、保留、依赖、冲突或无效时间等会阻止自动归档。稳定偏好和个人事实不因普通 30 天期限自动失效。归档仍保存正文，不等于永久删除。
- 首次纳管新生成的受管正文副本，从首份产生起固定 24 小时有效；重复查看、确认、重试和重启不续期。启用 P2 的运行实例先检查，随后约每 60 秒串行清理。占用、恢复证明不足或未知残留会保留 `cleanup_pending`。停机期间不保证按墙钟立即物理清除。
- 已终止且正文清理完成的普通准备元数据按规则保留 30 天；当前治理、首基线、删除依据和仍被恢复/退役流程引用的记录继续保留。不能把这一规则套用到所有会话、L4、预算或外部备份。
- 结构化记忆用 `suite_memory_revise` 更正、`suite_memory_purge` 永久删除。文档用 `suite_document_delete` 先预览，再按精确计划确认；默认保留原文件，删除原文件必须在计划中单独选择并确认。
- 文档删除覆盖选定项目及逻辑路径的受管索引、历史、登记备份和暂存，删除依据不随旧快照一起回退。`deleted` 且 `cleanup.complete: true` 才代表该计划范围内完成；`cleanup_pending` 不代表全部清理完成。原文件状态另列。

用户原话、助手复述、原生聊天、第三方插件副本、外部备份及模型供应商已接收内容不属于上述记忆删除的全局抹除范围。文件占用与存储介质特性也使逻辑删除不等同于取证级擦除。普通 Shell 或外部程序绕过受管入口的读写不在防复活保证范围内。

# Windows Alpha.2 archive acceptance

This folder contains independent acceptance operators. It does not modify the installed program to expose test modes. Generated files and installations are restricted to the designated real D: project output root.

The tested archives are `windows-package.2`. Both actual ZIP installations and their installed runtimes passed. The final desktop r3 runs passed actual workspace, Node second-entry, original VBS second-entry and normal-exit checks. Both reports deliberately remain `status: blocked` with `coreStatus: pass` because direct `start.ps1` was refused by this machine's PowerShell execution policy. No Windows policy or product file was changed. Earlier r2 receipts remain intact, but their workspace-ready claim is withdrawn: the old text-length predicate also accepted the actual 24-character loading screen.

`safe_extract.py` derives the member policy from the previous release extractor (source SHA-256 `94bffe1b90bf71ebeda343e910ec1f939750ac7beca7acf9d580623ef48d0df`). The new operator binds a regular, single-link archive before/after through its held file, rejects aliased output parents, scans all names/types/declared limits before creating the destination, rejects case aliases and file/directory conflicts, verifies CRC while copying, and never removes an existing or partial tree. This protects against archive contents; it is **not** a sandbox against another hostile process of the same Windows user.

`safe_extract_test.py` runs real ZIP/filesystem negative cases. The 30-definition suite has a retained missing-implementation RED and final GREEN. Intermediate failures were retained: Windows Python `lstat` and `fstat` expose different `ctime` semantics, so change times are now compared before/after within each source; the initial backslash fixture was normalized by Python's writer and was corrected to patch the actual ZIP directory bytes.

`bundle-audit.mjs` independently checks schema 3, the pinned graph/descriptor, complete payload-plus-donor coverage, every payload/support file, and the exact archive member inventory. Its 10-definition real-file suite has a retained RED and GREEN. It does not trust an installer's own success flag as evidence that source bytes were correct.

`install-archives.mjs <D:\...\SPEC.json>` accepts a schema-1 specification with `expected` (`hostVersion`, `sepVersion`, `revision`), fixed `python`, fresh `outputRoot`, two `archives` (`kind: full|sep`, `path`, `sha256`, `size`), `hostRoot`, and optional `guardRecords`. Guard records may refer only to public `launch.mjs` / `deployment-rc2.json` entry metadata. It validates the actual ZIP, extracts into a fresh directory, imports the actual extracted `installer.mjs`, installs into a new directory, verifies all program/support bytes and generated blank configuration, checks the required donor files before/after, and freezes the two independent configurations in `RESULT.json`.

The install operator does not launch a Host or Electron. A successful install-only receipt is not a desktop or default-startup result. In particular, a later `readCredential:false` headless diagnostic must not substitute for the actual blank-key default entry. Existing daily credentials, sessions and workspace content are never read by these operators.

Before installation it also runs the real extracted installer's existing-target refusal for each package, and the Only installer's first-required-file corruption refusal against a one-file synthetic donor. It never tampers with the official source. After installation, `runtime-smoke.mjs` executes the installed Node and pnpm (`24.21.0` / `11.7.0`), plus the primary runtime's own Node/pnpm. Python is located under the installed `runtime/primary-runtime/dependencies/python` and its version/import package versions are compared with that installation's `runtime.json`; isolated offline imports disable bytecode and user-site loading. Both actual final-archive installations passed these five commands, including Python `3.12.14` and 13 distribution imports per installation.

Evidence is under `D:\AIData\ProjectWork\DSH\alpha2-windows-packages-20261015-r1`. Each result binds the actual archive or prior result SHA-256; failed attempts remain unchanged.

Workspace readiness is recorded for each final round as `workspaceReadiness`; `workspaceSourceBinding` binds the four installed official frontend/renderer/layout/sidebar files. The verifier requires the real root/sidebar/main slot structure, absence of boot/spinner and slot/factory errors, and an enabled new-session button with a visible rectangle under the actual sidebar. It does not require a rectangle for the root anchor, which intentionally uses `display:contents`. Both Chinese and English button labels are fixed from the packaged dictionary. `headless-probe.mjs <install-RESULT> <SHA256> <fresh-output>` starts the two actual coordinated Hosts and checks the real budget, memory, composition and shutdown RPC. It is deliberately labeled `readCredential:false` diagnostic evidence and does not substitute for default startup.

`default-desktop-probe.mjs <install-RESULT> <SHA256> <full|sep> <fresh-output>` executes the actual installed `launch.mjs --inspect-desktop`; this is the existing launcher observation option, with ordinary `readCredential:true` behavior and the generated empty `.env`. The exact Electron process is verified by its app path and isolated userData before inspection or actions. Two rounds per installation were completed serially. Neither pointer input, tray clicks, the first close notice, nor an initial launch without the observer flag is thereby certified. It never kills global processes, injects a fake key, replaces the production main, or requests a model. Failed acceptance and subsequent cleanup are recorded separately.

Inspector startup is first identified without loading Electron (PID, executable, Electron version, browser-process role, application argument). A narrowly classified `MODULE_NOT_FOUND` while loading Electron is treated as pending only during bounded startup; no UI actions occur until exact app path/userData identity and readiness are established. Other errors remain failures. This addresses a previously observed inspection timing hazard; it is not evidence of a new Windows product bug.
# Windows long-path validation update

The first actual Full ZIP validation stopped before installation because the bundled Python could not open a member whose absolute extraction path exceeded the normal Win32 path limit. The failed output is retained under `fresh-install-verification-r1`. The extractor now applies Win32 extended path syntax only to validated filesystem operations, retaining ZIP path and parent alias checks. A real long-directory ZIP case reproduced the failure before the change and passed afterward.

The direct regression has 30 passing definitions. The unchanged junction fixture is separately **blocked**: Windows rejected its PowerShell setup with WinError 225. Its historical pass is not promoted into a current pass, and the blocked command was not rewritten or bypassed. `safe_extract_regression.py` records this distinction explicitly.

This validation extractor does not certify ordinary Windows Explorer extraction. Long member paths remain a delivery consideration; actual package installation uses the packaged Node installer and must independently prove its destination I/O. All failed fixtures are retained.

The default desktop probe also exercises the original packaged wrappers as second entries after exact window/Host ownership is established: round 1 runs `powershell.exe -NoProfile -File start.ps1`, and round 2 runs `wscript.exe start.vbs`. The original VBS contains its own child-process `-ExecutionPolicy Bypass`; the test adds no such parameter to the direct PowerShell case and changes no persistent policy. A security rejection is retained, never retried with alternate bypass commands. Wrapper process exit and actual same-window/same-Host reactivation are separate assertions. VBS's asynchronous PowerShell descendants are not independently tracked, so the resource result remains limited to the explicitly tracked processes and P2 lock.

The policy classification requires the original PS1 entry, exit code 1/no signal, and all three explicit markers: `SecurityError`, `FullyQualifiedErrorId: UnauthorizedAccess`, and the `about_Execution_Policies` explanation. It also verifies that the original Host/Electron/window still exists unchanged and the failed wrapper has ended. This path does not claim window reactivation. Other errors, including any VBS failure, still fail core acceptance. Inspector disconnection precedes the bounded exit wait; main-launcher exit 0 is checked separately from a failed-but-ended wrapper.

## Retained failures and correction boundaries

- `fresh-install-verification-r1`: validation extractor Win32 long-path failure before installation; extended-path I/O fixed only after a real failing regression. `fresh-install-verification-r2` is the successful installation of the old revision, not final revision-2 evidence.
- `headless-install-verification-r1` and `headless-start-diagnostic-r1`: old package startup failed. The diagnostic's raw Host error was `SEP_DAILY_INITIALIZATION_BLOCKED`; it did not itself reveal the underlying scope code. A separate real project-binding regression proved the installer placed the budget parent around another protected root. The new installer uses the disjoint `state/budget/budget.json` path; original failed data and ZIPs remain intact.
- `headless-install-verification-r2`, `r3`, and `r4`: real Hosts started and subsequently closed normally, but validation assertions used the wrong project ID field, conflated memory preferences/configuration/effective state, or used the old settings plugin name. Their results remain fail. `inventory-diagnostic-r1` captured actual public metadata before the final exact assertions were independently reviewed and frozen. The final probe binds recovery `id/root/memoryKey`, all three memory policy layers, and five exact Loader entry identities including the installed settings module URL.
- `default-desktop-full-r1`: the original PS1 policy rejection failed acceptance. The test's failure cleanup waited while its Inspector was still attached and reported blocked. Original results remain unchanged; later PID/lock observations and the separately captured guardian journal are subsequent evidence, not a rewrite. The final probe's cleanup ordering and launcher/wrapper evidence separation were reproduced and fixed before the two final desktop reports.
- Both `default-desktop-*-r2` receipts: their text length 24 and preloads were insufficient to prove workspace readiness. That claim was withdrawn. The exact historical predicate was rejected by targeted tests, the corrected source-bound r11 verifier was independently reviewed, and both final r3 runs then exercised the real workspace without product changes or longer deadlines.

No original daily library, credential, session content or official application process was used. The two public daily entry fingerprints were checked unchanged. Paid models and physical desktop input remain untested.

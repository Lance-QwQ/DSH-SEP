# macOS 首次安装用户入口：最小接线方案

状态：方案，尚未实现或认证。r48 的 19 个固定定义验证的是原生事务及两个修复回归；完整 r44 应用安装、首次启动、用户安装入口分别是不同证据。本方案不修改已经冻结的 r44 应用、first-install.mjs 或 install-native.c。

## 目标与边界

交付一个独立的“安装 DSH SEP.app”，供用户先安装、后启动。它内含未经启动的固定完整应用、外部 PACKAGE-INVENTORY、PROGRAM/BOOTSTRAP 摘要和最小可信安装控制器。完整应用藏于安装器 Resources 下，用户正常路径只会看到安装入口。

唯一产品目标为系统账户记录中的 ~/Applications/DSH SEP.app；唯一业务数据位置仍为 ~/Library/Application Support/DSH SEP/alpha2-mac-finder-preview。账户 home 来自 getpwuid / os.userInfo().homedir，不能由 HOME、环境变量、CLI、文件选择器或模型参数覆盖。安装器只处理当前用户，不提权，不操作官方 DSH。

这不是自动升级器。目标已有任意文件、目录、链接或同名应用即拒绝；业务数据根已存在即拒绝首次安装。不能为了继续而删除数据、修改 PROFILE、改 HOME，或把复制后的程序伪装为原目录。已发布事务的恢复另按下文处理。

当前 Profile 把绝对 programRoot、hostRoot、bundleRoot 和 helperPath 写入绑定。用户若先从下载位置启动完整应用，再移动到最终目录，可能得到 SEP_MAC_PROFILE_BINDING。因此：

- 第一次运行完整应用必须发生在固定最终位置。
- 安装器的校验不得启动内附应用、宿主、插件或模型。
- 如果用户自行进入安装器包内容并提前启动内附应用，安装器将因已有固定数据根拒绝，而不是替其迁移。
- 同一账户两份应用仍共用固定数据根与租约；此入口不提供同账户多实例。

## 最小包装及信任入口

新增独立 installer-entry 目录，包含一个小型 AppKit 外壳、固定安装控制器和私有 IPC。复用已经通过验证的事务 API 和应用清单验证器，不调用裸 Electron、不接受任意 shell 命令。

安装器自己的运行闭包必须有单独的编译期绑定清单：固定 Node、安装 helper、控制器及其全部 imports 的摘要；另绑定内附应用清单原字节摘要、PROGRAM、BOOTSTRAP、完整包来源检查点和支持的 OS。完整应用的外层二进制不改字节。

Node 可以使用包内一份固定 runtime，但执行前须由原生入口核验确切位置、普通文件身份和摘要；不能为完成验证而先执行未经绑定的候选 Node 或任意文件。最直观的第一版是安装器自带最小安装 runtime，避免依赖用户 PATH/Node 和完整应用尚未核验的入口。

安装器不得提供外部 argv 配置。生产原生入口从自身 NSBundle 推导固定闭包，忽略或拒绝额外参数。测试路径注入仅存在于独立测试构建，不进入交付编译。

目前 ad-hoc 签名和编译期摘要仅证明已绑定字节的一致性，不证明发布者身份。Release/checkpoint 的独立来源绑定仍须保留；Gatekeeper、quarantine、App Translocation、Developer ID 和公证不能因为内含安装器而被称作已解决。安装器不得移除 quarantine、重新签名内附应用或关闭系统检查。

## 用户流程

1. 打开安装器，显示支持平台、候选 DSH/SEP 版本、固定安装路径、固定数据位置、预期占用和“首次安装；不覆盖已有应用或数据”。
2. 只读检查内附完整包、当前账户、目标/数据缺失状态、父目录及可用空间。空间预检只给出保守提示，不能代替真实 I/O 错误处理。源与目标父目录重叠时提前拒绝。
3. 显示具体计划和摘要，用户点击“安装到当前用户的 Applications”。确认绑定该候选、账户、父目录条件、固定目标、数据根缺失条件以及可产生的安装记录/暂存位置。
4. 取得租约后重新核对确认内容，调用 executeFirstInstall。任何包字节、身份、路径或缺失条件变化都使计划失效，回到审阅，不自动确认新计划。
5. 仅在事务回执 committed 且实际 helper 收尾已确认后显示“安装完成”。再显示独立的“打开 DSH SEP”按钮。没有该动作，不自动启动。
6. 点击打开时重新核对最终应用身份和清单；使用 LaunchServices 打开固定目标，不启动下载目录或暂存目录的副本。open 返回成功只表示请求被接受，不能标为应用已就绪。

安装后健康状态由真实产品 owned/ready 回执、同代次租约、实际 NSRunningApplication 身份和退出证明判定。用户入口可以显示“已安装，启动状态待确认”，不能将安装成功与业务健康合为一个 pass。

### 父目录尚不存在

原事务 prepare 要求父目录已存在；用户入口不应隐式创建目录后声称预览完全只读。最小上层计划显式记录：

- 当前系统账户 home 的真实身份；
- ~/Applications 缺失这一前提；
- 唯一允许新增的目录及 0700 模式；
- 创建后才能生成下层事务计划这一派生关系。

用户确认后，由固定原生 mkdirat(O_NOFOLLOW 逐级验证) 路径建立唯一目录。EEXIST 不转换为“已成功创建”：重新回到审阅，防止确认期间第三方建立父目录。创建后记录真实身份，再生成下层 core plan；它必须与已确认上层计划的全部候选/路径/账户/缺失条件吻合，持久记录二者摘要关系后才执行。没有新增候选或路径授权。

若第一版不实现这项上层计划，则应明确要求父目录存在并给出创建提示，不能直接用普通递归 mkdir 隐式绕过审阅。此选项影响易用性，不影响核心事务验证结果。

## 计划保存与恢复

安装状态与业务数据分开。使用系统账户下独立、0700、真实路径的安装治理目录，例如 ~/Library/Application Support/DSH SEP Installer；文件 0600、单链接、拒绝别名。该目录的创建也写入上层计划的固定副作用范围。

持久记录上层确认、下层 plan、完整清单及摘要、事务 id、父目录身份和对应 journal locator。完整清单采用独立受限文件并保留摘要，不把无限大小 JSON 直接塞进单帧 IPC。具体上限须按 PACKAGE-INVENTORY 的现有 100000 条上限和实际包大小定死后测试，不复用业务正文入口。

写入顺序为“确认记录可靠落盘 → 下层计划可靠落盘并绑定 → 执行”。当前 core journal 位于同父私有 .dsh-sep-install-transactionId，只有它证明实际阶段。上层索引丢失、记录损坏或摘要不匹配时不能根据路径前缀猜测、收养或删除暂存目录。

重开安装器只读取经身份与摘要验证的自身活动事务，给出“恢复本次安装”。不得接收用户输入任意 plan 路径，也不得把任意旧目录认作可恢复。

| 下层事实 | 用户入口行为 |
| --- | --- |
| 未开始执行 | 用户可取消；不创建最终应用，不运行程序。 |
| copying 或来源/状态无法验证 | blocked；显示固定分类及位置，保留现场。第一版没有复制中断后的自动重做/清理。 |
| verified，暂存完整且目标缺失 | 再校验已确认计划后调用 recoverFirstInstall，使用不覆盖发布。 |
| publish-intent / published，目标身份等于已验暂存 | 只核对目标、补完安装记录；不重新复制，不删除数据，不重复启动。 |
| committed，最终内容仍相符 | 显示已安装和独立打开按钮，不再次执行首次安装。 |
| 现有目标属于其他事务，或源/父/目标身份改变 | blocked；原状保留，不能改用自动升级或数据迁移。 |

最终 rename 后用户可能手动打开应用，甚至在 committed 记录前产生业务数据。恢复只能根据已发布目标身份补完记录；不得因为数据根存在而删除已发布应用、回滚数据或重建 Profile。尚未发布的首次安装仍必须因数据出现而拒绝。

## 进度、关闭与未知收尾

第一版 core 没有公开的 abort API。安装器不能把“停止等待”伪装成“安装已取消”，也不能在用户以为取消后继续偷偷发布。

- “取消”仅在执行前提供。
- 执行期间显示明确阶段；关闭进度窗口只在用户明确选择“后台继续安装”后允许，控制器仍持有租约。
- 正常退出安装器时，已启动的事务必须实际完成或返回有界 blocked；不能因 UI 关闭释放租约。
- 超时、IPC 丢失、收尾未知时，保持现场和 blocked。不要杀死未知进程、重复 helper 或自动重试发布。
- 强制终止/系统崩溃由下一次显式恢复处理。完成 helper 实际退出与 JS 控制器退出后，才能声称安装器自己的资源释放；不宣称全系统零残留。

后续如果确需执行中取消，应另加 core 可证明的取消协议及实际复制/发布窗口测试。不能以 UI cancel 回调代替这一能力。

## 最小实现顺序与验收定义

先实现入口契约及计划/恢复状态机，再接原生 UI，最后使用固定完整包验证。三阶段均先保留失败证据，后实现并封存。

1. 路径准入：真实账户固定目录；忽略 HOME；任意 argv/目标/数据覆盖拒绝；官方 DSH 合成哨兵不变。
2. 闭包准入：安装器 Node/helper/控制器或候选清单变化在启动任何候选代码之前拒绝；未知 OS/架构拒绝。
3. 预览绑定：取消不执行；确认前后包变化、目标出现、dataRoot 出现、父目录替换均失效。
4. 父目录创建：缺失确认后仅创建固定 Applications；竞争创建不接管；别名/ACL/写权限异常拒绝；中断记录可判定。
5. 真实完整应用：r44 清单及签名完整验证，无覆盖复制到最终路径，源字节不变；之后才首次启动。
6. 两层计划落盘：在确认后/下层计划落盘后/执行前杀控制器，重开不得自动执行未经持久确认的安装。
7. 恢复：复用原生 verified/published SIGKILL 正例；copying/损坏记录保持 blocked；已发布后数据根出现只补记录。
8. 重复入口：第二安装器不得覆盖第一实例的状态或绕过 native 安装锁；现有应用不被覆盖。
9. 关闭：执行前取消、执行中后台继续、IPC 中断、helper 未知收尾分别验证，不把超时当取消成功。
10. 最终启动：LaunchServices 指向固定 installed app；PROFILE 精确绑定最终目录，实际 ready/正常退出与安装回执分别统计。
11. 已在下载目录启动：固定 dataRoot 已有绑定时首次安装拒绝，原库/账本/配置保留；不测试性清空后冒称成功。
12. 实际下载体验：隔离真实账户验证 quarantine/Gatekeeper/Translocation。未签名/未公证限制照实保留，不删除属性规避。

自动 macOS VM 可以证明原生事务、实际 AppKit 与 LaunchServices 行为；物理 Mac 的 Finder/系统安全交互另需证据。首装入口完成不等于 Only SEP 包、自动更新、卸载、Intel 兼容或完整 macOS 公共认证已完成。

## 本轮建议

先完成当前 r44 完整应用的固定最终目录安装与真实启动验证，再制作上述独立安装器。保持应用 payload 原字节，仅新增包装层和其证据。若完整包出现复制/签名/首启失败，先据实修正对应路径，不用安装 UI 掩盖问题。
